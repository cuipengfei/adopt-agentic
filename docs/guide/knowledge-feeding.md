# 知识喂养：把你的大脑装进 Agent

> **上下文视角**：无论用哪条路径注入知识，最终都是往上下文里放信息——区别在于**什么时候放、放多少、放多久**。

到目前为止，我们讨论了上下文的各种载体：System Instructions、工具、MCP、Skills……它们各自为战。但你作为使用者，面临的问题是统一的：

**我有一堆关于项目的知识、团队的规范、个人的偏好，怎么让 Agent 系统性地知道这些？**

这就是"知识喂养"。它不是一个独立的功能，而是将前面讲到的各种上下文载体组合起来，形成一套为 Agent 提供领域知识的策略。

## 为什么需要统一视角

Agent 的能力上限，取决于它拥有的高质量上下文。LLM 自身的通用知识好比互联网，而你喂给它的知识，是你们公司的内部 GitLab、Confluence 和 Slack 频道——没有这些，它不可能干好具体的活。

前面几章介绍的机制，是从 Agent 的角度看"我能吃什么"。现在我们换到你的角度看"我该喂什么，以及怎么喂"。

如果说上下文像牛奶，新鲜时营养丰富，放久了会变质。那么知识喂养就是建立一个现代化的乳品供应链——在正确的时间，通过正确的管道，输送正确剂量的新鲜牛奶。

## 三条核心路径

要把你的知识喂给 Agent，主要有三条路径，每条对应了前面讲过的一种或多种机制。

| 路径 | 核心机制 | 持久性 | 体量 | 结构化程度 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **规则层注入** | `System Instructions` | 始终存在 | 小 (几 KB) | 低 (自然语言) | 项目级规范、角色设定、安全护栏 |
| **能力层扩展** | `Skills` | 按需加载 | 中 (几十 KB) | 中 (指令+流程) | 特定领域工作流、最佳实践 |
| **数据层检索** | RAG (通过工具实现) | 按需检索 | 大 (GB/TB) | 高 (结构化/向量化) | 文档库、API spec、代码库、知识图谱 |

我们来逐一解析。

### 1. 规则层注入 (System Instructions)

这是最直接、最基础的知识喂养。通过修改 `CLAUDE.md`、`copilot-settings.json` 或类似文件，你定义的规则会成为 Agent 的一部分，在每次会话开始时自动加载。

- **做什么**：定义 Agent 的行为准则、身份、口吻，以及不可逾越的红线。
- **怎么喂**：用自然语言编写项目规范、编码约定、commit message 格式等。
- **例子**："所有代码必须遵循 aio-libs 社区规范"、"禁止在 `.py` 文件外使用 `import`"、"总是先写测试"。

这种方式适合注入那些**全局、高优先级、必须时刻遵守**的知识。它构成了 Agent 世界观的基石。

### 2. 能力层扩展 (Skills)

如果说规则层是给 Agent "立规矩"，能力层就是给它"请家教"。

当你加载一个 Skill（例如 `git-master` 或 `frontend-ui-ux`），本质上是动态地向 Agent 的 System Prompt 中注入了一大段特定领域的专业知识和行动指南。

- **做什么**：教会 Agent 在特定场景下如何思考和行动，比如如何进行 git rebase，或者如何选择合适的 CSS 布局。
- **怎么喂**：编写或安装一个 Skill，其中包含了该领域的最佳实践、决策流程和常用命令。
- **例子**：加载 `mermaid-diagrams` skill 后，Agent 就"知道"了如何使用 Mermaid 语法创建各种图表，并能在你要求"画个流程图"时，产出符合语法规范的代码。

它适合封装那些**特定任务场景下才需要**的、成体系的知识。

### 3. 数据层检索 (RAG)

规则层和能力层处理的都是"如何做"的知识，但对于"是什么"的大量事实性信息（比如整个代码库、几百篇 API 文档），它们就无能为力了。这需要数据层检索，也就是大家常说的 RAG (Retrieval-Augmented Generation)。

Agent 通过内置工具（如代码搜索、文档查询）实现 RAG。当你问"我们的支付接口有哪些状态？"，Agent 不会去猜，而是：

1.  **调用工具**：执行代码搜索，查询 `PaymentStatus` 枚举的定义。
2.  **结果注入上下文**：将搜索到的代码片段放入 `messages` 数组。
3.  **LLM 基于结果回答**：LLM 看到代码原文后，总结出所有状态并回答你。

- **做什么**：让 Agent 能按需访问海量的、动态变化的结构化和非结构化数据。
- **怎么喂**：维护好你的数据源，并确保 Agent 有合适的工具去检索它们。比如，让你的代码对 Agent 更友好（`agent-friendly code`），或者提供一个 `llms.txt` 文件来指明关键信息的位置。
- **例子**：Agent 通过 `grep` 工具在代码库中搜索 `TODO`，将结果注入上下文，然后为你生成一个待办事项列表。

这是处理**大规模、事实性知识**的唯一有效途径。

## 选择标准：什么时候用什么

| 如果你的知识是... | 就用... | 因为... |
| :--- | :--- | :--- |
| **全局规则**，必须时刻遵守 | **规则层注入** | 它能确保知识在每次会话中都强制生效。 |
| **特定领域的方法论**或工作流 | **能力层扩展** | 它能在你需要时加载，任务结束后卸载，不污染通用上下文。 |
| **海量、具体、事实性**的信息 | **数据层检索** | 它能让 Agent "即用即查"，避免用有限的上下文窗口硬背大量数据。 |

一个成熟的 Agentic 工作流，总是这三条路径的组合。

## 横切关注点

- **上下文流动**：消耗你提供的项目文档、内部规范、领域经验；根据不同路径，将它们转化为持久的 System Instructions、按需加载的 Skill 指令、或即时检索到的数据片段，注入上下文窗口。
- **风险提示**：知识注入过多会挤占推理空间（"attention dilution"），过少会导致 Agent 基于通用知识"臆造"不符合项目实际的答案。知识的质量、新鲜度和相关性至关重要。
- **可审计性**：知识来源必须可追溯。当 Agent 做出一个决策时，你应该能清楚地知道这个决策是基于哪条规则、哪个 Skill 的指导，或是检索到的哪段具体数据。
