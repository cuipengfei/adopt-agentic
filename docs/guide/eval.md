# 验证与可观测性

> **上下文视角**：验证结果本身就是上下文——exit code、测试报告、lint 输出，全部回注入 messages，驱动 Agent 的下一步决策。

上一节说了：Sub Agent 返回的是摘要，不是真相。那怎么知道它干对了？

不只是 Sub Agent。Agent 的每一步输出——每次工具调用、每个任务结果——都可能是错的。验证机制就是兜底的安全网。

## 逐步验证：从命令到任务

验证不是最后一步才做的事。它贯穿 Agent 工作的每一步，粒度从细到粗。

### 第一层：每条命令，跑对了吗？

Agent 每调用一次工具，系统会自动检查结果。

- **验证对象**：单次工具调用（`bash`、`read_file`、`write_file`……）
- **成功信号**：exit code 为 0、文件读取成功、API 返回 200
- **失败动作**：错误信息回注上下文，Agent 自动调整

```json
// → REQUEST (Agent 决定调用工具)
{
  "role": "assistant",
  "tool_calls": [{ "name": "bash", "arguments": { "command": "npm install" } }]
}

// ← RESPONSE (工具执行结果回注入下一轮上下文)
{
  "role": "tool",
  "name": "bash",
  "content": "exit code: 1\nnpm: command not found"
}
```

LLM 在下一轮看到这个 `tool` 消息，知道 `npm install` 失败了——找不到 `npm`。基于这个新上下文，它决定改用 `bun install`。

这一层是全自动的，不需要你参与。但它是整个验证体系的地基：如果这一层的信号没有正确回注上下文，后面所有层都会失灵。

### 第二层：整个任务，真的完成了吗？

单条命令成功 ≠ 任务完成。

`edit_file` 执行成功，不代表重构对了——得跑测试才知道。`bash deploy.sh` 返回 exit code 0，不代表部署成功——得访问 URL 看是否返回 200。

- **验证对象**：完整任务的最终意图
- **成功信号**：外部世界的真实标准（测试通过、build 成功、API 可达）
- **失败动作**：失败信号回注上下文，Agent 进入修正循环（上一节讲的迭代模式）

关键点：**任务级验证的 pass/fail 也必须回注入上下文。** 如果 Agent 跑完测试但看不到测试结果，它就无法判断任务是否真的完成。

```json
// Agent 跑完测试，结果回注入 messages
{
  "role": "tool",
  "name": "bash",
  "content": "exit code: 1\nFAILED tests/auth.test.ts > should reject expired tokens\nExpected: 401, Received: 200"
}
```

Agent 看到这条消息，知道重构破坏了过期 token 的校验逻辑，然后针对性修复。

作为使用者，你要做的是**告诉 Agent 什么叫"做完了"**：
- 跑哪个测试命令（`bun test`、`pytest`）
- 跑哪个 lint 检查（`eslint .`、`tsc --noEmit`）
- 检查什么文件状态

你定义"完成"的标准越清晰，Agent 自我验证的能力就越强。

### 第三层：系统整体，靠谱吗？

前两层关注单次任务。第三层退后一步，看全局。

你用了一段时间 Agent，开始关心这些问题：
- 这个任务花了多少 token？是不是太贵了？
- Agent 平均需要多少轮工具调用才能完成一类任务？在变好还是变差？
- 它是不是在两个方案之间反复横跳？

这就是可观测性——对 Agent 行为模式的持续监控。

- **验证对象**：Agent 的长期行为模式和资源消耗
- **成功信号**：完成率上升、平均步骤数下降、token 消耗合理
- **触发动作**：发现异常模式时降级策略、暂停任务、或转人工

有些 Agent 工具内置了基础的可观测性（token 计数、执行时间）。更专业的场景可以接入 LangSmith、LangFuse 之类的平台做深度分析——但对大多数使用者来说，关注 token 消耗和执行轮数就够了。

## 验证金字塔

越底层越自动化，越顶层越靠人。

### Level 1: 语法与执行
Agent 自动检查。能跑吗？报错吗？

陷阱：**没报错 ≠ 成功**。`rm` 删错文件不报错，逻辑有问题的脚本照样跑通。

### Level 2: 逻辑与语义
测试检查。功能对吗？边界条件处理了吗？

盯紧一件事：Agent 修的是**根因**还是**表象**？有些 Agent 为了让测试过会删测试用例或把超时改长。

### Level 3: 意图与价值
人来检查。这真的是我想要的吗？

没法自动化。Agent 完美实现了一个你不需要的功能，也是失败。

## 错误恢复

Agent 会犯错。关键是它能不能自己爬起来。

一个反直觉的发现：**别急着擦掉错误。** 失败的尝试留在上下文里，反而能帮 LLM 避免重蹈覆辙——它从失败记录中隐式学习"这条路走不通"。盲目清理对话历史有时候适得其反，因为你同时抹掉了宝贵的负面经验。当然，这不意味着永远不清理——上下文窗口终究有限。关键是区分"已过时的噪声"和"仍有参考价值的失败记录"。

**回滚**：任务级验证失败时，回到最近的已知好状态。比如代码重构破坏了测试，Agent 用 `git checkout` 撤销修改，换个思路重来。核心是在动手前建立回滚点——这是 Agent 自己应该做的事，好的 Agent 会在大改之前先确认 git 状态干净。

**死循环识别**：如果 Agent 反复尝试同一个方法但持续失败（达到重试阈值），它应该停下来换思路，而不是继续撞墙。你看到 Agent 说"我似乎卡住了"——这是好事，说明它识别了死循环。

**假完成**：最棘手的失败模式。Agent 说"搞定了！"，但任务级验证显示失败。通常是因为验证步骤没有被强制执行——Agent 跳过了测试就宣布完成。解决方案：在你的指令中把验证步骤写成强制要求（"修改完必须跑 `bun test`，测试全过才算完成"），确保验证结果回注上下文。

回滚、换路、强制重跑——这些错误恢复动作的本质都是上下文减法：从对话历史里切掉错误路径带来的污染。

但还有一种隐性的减法你可能没注意到：长对话中 agent 会自动压缩早期历史来防止窗口溢出。代价是你最初写的约束可能被压没了。如果 agent 在对话后半段突然"忘了"一开始的规则，八成不是它笨，是那条规则已经不在上下文里了。实操：长任务中隔一段时间就重申核心约束。或者在它犯错时，把原始指令和它的错误行为一起发给它，让它自己对比。

### 恢复策略：回滚、修正还是重来

Agent 搞砸了。下一步怎么办？不是所有错误都该用同一种方式处理。

| 状况 | 推荐做法 | 理由 |
|------|---------|------|
| 改动范围小，错误明确 | 原地修正 | 最快，上下文还热着 |
| 改动范围大，方向正确但细节有误 | 局部回滚 + 修正 | 保留正确的部分，只撤销出问题的 |
| 方向本身就错了 | 彻底重来（新会话） | 继续修补只会越修越歪 |

选哪条路取决于一个判断：**错在哪一层**？工具调用参数写错了，修一行就行。整体方案思路跑偏了，修一百行也救不回来——不如重新开始，把失败的尝试作为"负面经验"喂给新会话。

### 验证闭环

验证不是"做完了跑一下测试"。验证是一个循环：执行 → 验证 → 反馈 → 修正 → 再验证。

闭环的关键在**反馈回注**。Agent 跑完测试，结果必须回到上下文里——通过了，知道可以继续；失败了，知道哪里出了问题。如果验证结果没有回注，Agent 就是闭着眼走路。

一个完整的验证闭环：
1. Agent 完成修改
2. 自动触发验证（测试、构建、lint）
3. 验证结果回注入上下文
4. Agent 基于结果决定：通过则继续，失败则修正
5. 修正后回到第 2 步

你要确保的是：第 3 步不能断。验证跑了但结果没喂回去，等于没验证。

## 常见反模式

### 假完成

**症状**：Agent 说"已完成！"但你检查发现功能没实现、测试没跑、或者跑了但失败了。

**后果**：你以为任务做完了，基于这个假设继续后续工作。等发现问题时，连带后续任务也得返工。

**修复策略**：在指令中把验证写成强制步骤——"修改完必须跑 `bun test`，测试全过才算完成"。关键是让验证结果回到上下文里，而不是让 Agent 自己"判断"是否完成。外部信号（exit code）比 Agent 的自我评估可靠得多。

### 死循环

**症状**：Agent 反复尝试同一个修复方法，每次都失败，但就是不换思路。你看到对话里同样的错误出现了三四遍。

**后果**：烧 token、烧时间，最终还是失败。更糟的是，对话历史被相同的失败记录污染，上下文窗口被无效内容填满。

**修复策略**：设定重试阈值——"如果同一个方法失败两次，换一种思路"。或者更直接：看到死循环迹象就人工介入，告诉 Agent 别再试了，给一个新方向。有些 Agent 会自己识别死循环并报告"我卡住了"——这其实是好行为，比闷头撞墙强。

### 速度陷阱

**症状**：Agent 生成代码的速度极快，但代码质量在下降——变量命名随意、边界条件没处理、风格和项目不一致。

**后果**：短期看效率高，长期看维护成本翻倍。你花在 review 和修补上的时间，可能比手写还多。

**修复策略**：验证的密度要跟上生成的速度。Agent 改了代码，立刻跑测试、跑 lint、跑类型检查。自动化验证覆盖不到的地方（命名、设计意图、架构一致性），由你在关键节点做人工 review。不是每次都要 review，但每隔几个任务抽查一次。

## 读每一节时，留意这三件事

- **上下文流动**：每一层验证都产生信号（exit code、测试报告、指标），这些信号回注入上下文，成为 Agent 下一步决策的依据。验证不是事后审计，是实时导航。
- **风险**：验证不足是 Agent 项目失控的根源。一个工具级的小错误，如果没在早期捕获，会在后续步骤中被放大——最终导致整个任务的灾难性失败。
- **可审计性**：三层验证的日志构成完整的审计链。工具调用的输入输出、任务验证的成败记录、可观测性指标——这些让你能追溯 Agent 在每个决策点上"看到了什么、做了什么、为什么"。
