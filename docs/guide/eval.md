# Eval: 验证与可观测性

> **上下文视角**：验证结果本身就是反馈上下文 — 告诉 Agent 做对了没，以及下一步该怎么修正。

Agent 的工作不是一次性黑箱操作，而是一系列可验证的步骤。作为使用者，理解验证机制，才能建立信任，并在它跑偏时及时干预。

验证不是一个孤立的动作，而是一个持续的反馈循环，贯穿 Agent 运行的始终。

## 验证的三个层次

想象你在指导一个初级程序员。你不会等他完成整个项目才 review，而是在不同阶段设置检查点。对 Agent 也一样。

### 层次 1：工具调用级验证 (Tool Call Validation)

这是最基础的检查。Agent 每调用一次工具（如 `read_file`, `bash`），系统都会进行健全性检查。

- **输入验证**：`read_file` 的路径存在吗？`bash` 命令安全吗？
- **输出验证**：工具执行成功还是失败？`bash` 命令的 exit code 是 0 吗？文件读取成功了吗？

这一层验证通常由 Agent 框架或工具本身自动完成。执行结果——成功或失败，连同返回值或错误信息——被打包成一个 `tool` 角色的消息，回注入上下文。

```json
// → REQUEST (Agent 决定调用工具)
{
  "role": "assistant",
  "content": "好的，我将执行 `npm install`。",
  "tool_calls": [{ "name": "bash", "arguments": { "command": "npm install" } }]
}

// (Agent 在本地执行 bash 命令)

// ← RESPONSE (工具执行结果被注入下一轮上下文)
{
  "role": "tool",
  "name": "bash",
  "content": "exit code: 1\nnpm: command not found"
}
```

当 LLM 在下一轮看到这个 `tool` 消息，它就知道 `npm install` 失败了，原因是找不到 `npm`。基于这个新的上下文，它可以决定尝试 `bun install` 或向你求助。

### 层次 2：任务级验证 (Task-Level Validation)

单个工具调用成功，不代表任务完成了。Agent 说“我搞定了”，真的吗？

“重构代码”任务成功，不是因为 `edit_file` 工具调用成功，而是因为重构后的代码通过了单元测试。
“部署应用”任务成功，不是因为 `bash` 命令执行无误，而是因为部署后的 URL 返回了 HTTP 200。

这就是任务级验证：**用外部世界的真实标准，来判断 Agent 是否达成了用户的最终意图。**

聪明的 Agent 会主动要求验证：

> “我已经将 `isValidUser` 函数移动到了 `validators.js` 并更新了引用。为了确认一切正常，我应该运行哪个测试文件？”

作为使用者，你需要为 Agent 提供验证手段。最常见的包括：
- 运行测试命令 (`npm test`)
- 执行 lint 检查 (`eslint .`)
- 调用 API 端点并断言响应
- 检查文件系统状态（文件是否存在、内容是否符合预期）

### 层次 3：可观测性 (Observability)

这是最高层次的“验证”——持续监控 Agent 的“生命体征”。它超越了单次任务的 pass/fail，关注的是整个系统的健康度和效率。

可观测性回答这些问题：
- **资源消耗**：这个任务花了多少钱（token 成本）？用了多长时间？
- **行为模式**：Agent 是否在两个方案间反复横跳？是否陷入了“编辑-测试失败-回滚”的死循环？
- **效果评估**：Agent 平均需要多少步才能解决一类问题？它的方案被你接受的比例是多少？

可观测性数据（日志、追踪、指标）通常被发送到专门的平台（如 LangSmith, LangFuse），让你能从宏观视角分析 Agent 的表现，而不是陷在单次对话的细节里。

## 可靠性 & 错误恢复

再强的 Agent 也会犯错。关键是它能否从错误中恢复。

- **回滚策略**：当任务级验证失败时，最安全的做法是回滚到上一个已知的好状态。比如，如果代码重构破坏了测试，Agent 应该能通过 `git stash` 或其他机制撤销所有文件修改，然后重新尝试。

- **死循环识别**：如果 Agent 连续三次尝试完全相同的步骤但都失败了，这很可能是一个死循环。一个健壮的 Agent 会识别出这种模式，暂停下来，然后说：“我似乎卡住了。我试了三次都未能解决问题，也许我们应该换个思路？”

- **“它说完成了，但其实没有”**：这是最棘手的失败模式。Agent 的最终回复可能是“任务完成！”，但任务级验证却显示失败。这通常源于上下文不足——LLM 看不到验证失败的信号。解决方案是确保验证步骤是 Agent 工作流的强制一环，其结果必须回注入上下文。

验证结果，无论是成功还是失败，都是驱动 Agent 前进（或修正方向）的最重要燃料。

## 横切关注点

- **上下文流动**：消耗=你提供的验证标准（如测试命令）；产生=pass/fail 信号、错误信息、性能指标，这些都作为新的上下文回注，指导下一步行动。
- **风险提示**：验证不足或缺失是 Agent 项目失控的根源。一个微小的工具级错误，如果没有在早期被捕获，可能会在后续步骤中被层层放大，最终导致整个任务的灾难性失败。
- **可审计性**：每一层验证的日志都是一条黄金审计线索。工具调用的输入输出、任务验证的成败记录、可观测性平台上的追踪图，共同构成了完整的、可追溯的操作历史。
