# Peer-to-Peer Agents

> **上下文视角**：上下文如何在平级 Agent 之间双向流动 — 不再是单向注入，而是互相交换，形成动态的、共享的认知。

在 [Sub Agent](./sub-agents.md) 的世界里，关系是清晰的层级结构：主 Agent 是将军，Sub Agent 是士兵。将军发号施令，士兵执行任务，然后报告结果。这是一种单向的、可预测的上下文流动。

Peer-to-Peer (P2P) Agents 模型则完全不同。它打破了层级，引入了一个更复杂、也更强大的协作范式：**平级协作**。

## 心智模型：层级式 vs 平级式

想象一个软件开发团队：

- **层级式 (Hierarchical)**：就像一个传统的瀑布模型团队。项目经理将任务分解，分配给前端、后端、数据库专家。每个人独立完成自己的部分，然后汇总给项目经理。这是典型的"分而治之"。Sub Agent 模型就是如此，它擅长处理可以被清晰拆解、依赖关系明确的任务。

- **平级式 (Peer-to-Peer)**：更像一个敏捷开发小组。一个前端专家、一个后端专家和一个测试专家坐在一起结对编程。他们没有明确的领导，而是通过持续对话、互相挑战、共享发现来共同推进一个功能。
  - 前端专家：“我需要一个这样的 API 接口。”
  - 后端专家：“这个接口设计在并发场景下会有性能问题，不如我们换一种方式...”
  - 测试专家：“你们俩说的我都懂了，我先根据这个新思路写两个集成测试用例，提前锁定行为。”

这种 P2P 模式下，没有绝对的“指挥者”，只有围绕共同目标的**多视角协作**。

## 为什么大多数工具选择层级式

既然 P2P 协作听起来如此强大，为什么我们日常使用的 Agent 工具（如 Claude Code, Cursor 等）大多仍基于层级或单 Agent 模式？

答案是：**协调开销 (Coordination Overhead)**。

1.  **通信复杂性**：`N` 个 Agent 的团队，潜在的通信渠道是 `N * (N-1) / 2`。3 个 Agent 是 3 条信道，5 个 Agent 就变成了 10 条。协调成本呈指数级增长。
2.  **错误传播**：在一个 Agent “幻觉”或跑偏时，它的错误结论会通过消息链迅速污染整个协作网络，导致集体跑偏。
3.  **调试困难**：当最终结果出错时，你很难定位是哪个 Agent 的哪个决策出了问题。这是一个分布式系统的经典难题——“到底是谁的错？”
4.  **成本**：多个 Agent 并行推理和通信，意味着多份并行的 LLM API 调用开销。

层级委派模型简单、可控、经济。对于绝大多数日常开发任务，它已经足够好。

## 什么任务值得平级协作

P2P 协作并非万能灵药，它只适用于特定类型的问题——那些**单一视角无法有效解决的复杂问题**。

一个简单的决策框架：

- **任务能被清晰拆解为独立子任务吗？**
  - **是** → 用层级式 (Sub Agent)。例如：“重构 A、B、C 三个独立的模块”。
  - **否** → 考虑平级式。

- **任务需要多个不同专业领域的知识融合吗？**
  - **是** → 考虑平级式。例如：“设计一个兼顾用户体验、技术可行性和商业目标的注册流程”。你需要一个“产品经理 Agent”、一个“设计师 Agent”和一个“工程师 Agent”共同商议。
  - **否** → 用层级式或单 Agent。

- **任务的目标是探索性的，没有唯一正确答案吗？**
  - **是** → 考虑平级式。例如：“为我们的产品构思三种可能的盈利模式”。多个 Agent 从不同角度进行头脑风暴，互相激发，比单个 Agent 线性思考更有效。
  - **否** → 用层级式。

P2P 的威力在于**视角碰撞**和**集体智慧**，而不是简单地并行执行。

## 这是前沿

坦率地说，我们正处在 Agentic 工作流演进的早期。P2P Agent 协作是业界公认的前沿方向，但相关的成熟工具和最佳实践生态尚未形成。

目前，像 `crewAI`、`AutoGen` 这类框架允许开发者构建多 Agent 协作系统，但它们更多是面向“构建 Agent 的人”，而不是“使用 Agent 工具的人”。

对于日常使用 Agent 辅助开发的我们而言，理解 P2P 的心智模型，其价值在于：
1.  **拓展想象力**：知道 Agent 协作的未来可能性。
2.  **识别场景**：在遇到真正需要多视角碰撞的复杂问题时，意识到当前工具的局限性，并可以手动“扮演”多个 Agent 的角色与主 Agent 对话。

## 上下文视角：双向流动的上下文

在 P2P 模型中，上下文的流动是双向的、网状的。

Agent A 的输出（`content`）不仅仅是返回给一个“上级”，而是作为输入（`messages`）进入 Agent B 和 Agent C 的上下文。Agent B 在此基础上推理，其输出又会影响 Agent A 和 C。

**── Agent A & B 协作：第 1 轮 ──**

Agent A (前端专家) 发起对话：

```json
// → REQUEST (Agent A → LLM API)
{
  "system": "你是前端专家...",
  "messages": [{ "role": "user", "content": "我需要一个获取用户信息的 API，最好是 `/users/{id}`" }]
}
```
*LLM 返回 Agent A 的思考，这个思考会被 P2P 框架捕获。*

**── Agent A & B 协作：第 2 轮 ──**

P2P 框架将 Agent A 的输出传递给 Agent B (后端专家)。Agent B 的上下文现在包含了 Agent A 的提议：

```json
// → REQUEST (Agent B → LLM API)
{
  "system": "你是后端专家，关注性能与安全...",
  "messages": [
    { "role": "user", "content": "前端专家提议：需要一个获取用户信息的 API，最好是 `/users/{id}`。请评估此方案。" }
  ]
}
```

LLM 基于 Agent B 的身份和收到的信息进行推理，提出挑战：

```json
// ← RESPONSE (LLM API → Agent B)
{
  "role": "assistant",
  "content": "直接暴露数字 ID 有安全风险（遍历攻击）。建议使用 UUID。另外，一次只获取一个用户，在列表页场景下会产生 N+1 查询，不如提供一个批量接口 `/users?ids=...`。"
}
```

Agent B 的这个响应，又会被框架送回 Agent A 的上下文，形成一个闭环。

这里的关键是：**上下文在对等体之间互相交换、互相构建**，最终形成一个比任何单个 Agent 的初始上下文都更丰富、更准确的共享认知。

## 横切关注点

- **上下文流动**：消耗的是各个 Agent 独立的初始上下文；产生的是 Agent 间通过双向消息传递而动态形成的共享上下文和集体发现。
- **风险提示**：协调开销呈指数级增长 (`O(n²)`), 沟通成本极高。一个 Agent 的错误或“幻觉”可能通过消息链被放大，造成集体跑偏 (cascading failure)。当出现问题时，在复杂的交互历史中进行根本原因分析和调试极为困难。
- **可审计性**：Agent 之间的所有消息记录（请求、响应、挑战、确认）都必须可追溯、可重放，否则整个协作过程将成为一个无法理解的黑盒。
