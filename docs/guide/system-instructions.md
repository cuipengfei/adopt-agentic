# 系统指令 (System Instructions)

> **上下文视角**：系统指令是注入每个 API 请求的“宪法”——它为 Agent 设定了身份、规则和目标，是 LLM 收到的第一份、也是优先级最高的上下文。

## 它是如何工作的

Agent 与 LLM 的每一次交互，都不是从零开始。在你的指令之前，一段特殊的上下文已经被注入了请求。这就是系统指令。

它在 API 请求中的物理形态是一个 `system` 字段：

```json
// → REQUEST（agent → LLM API）
{
  "system": "你是一个 AI 编程助手。你的名字是 Sisyphus-Junior。你的目标是帮助用户完成编码任务。你只编写或修改代码，从不回答与编程无关的问题。你遵循 Google TypeScript 风格指南。",
  "messages": [
    { "role": "user", "content": "帮我写一个斐波那契函数" }
  ]
}
```

看到那个 `system` 字段了吗？它就像一张印在每个信封上的便条，确保邮差（LLM）在读信（`messages`）之前，首先明确自己的身份和任务。无论对话进行多少轮，这份指令都雷打不动地存在于每次请求中，持续约束着 LLM 的行为。

## 它包含什么

系统指令通常包含：

- **身份 (Identity)**：你是谁？（例如，“你是一个资深前端工程师”）
- **能力 (Capabilities)**：你能做什么？（例如，“你能读写文件、执行终端命令、搜索代码库”）
- **规则 (Rules)**：你必须遵守什么？（例如，“所有代码必须包含 JSDoc 注释”、“不要修改 `package.json` 文件”）
- **目标 (Goal)**：你的最终目的是什么？（例如，“帮助用户构建一个功能完整的 Web 应用”）
- **输出格式 (Output Format)**：你应该如何回应？（例如，“代码修改用 diff 格式呈现”、“决策过程需要分点说明”）

这些内容共同构成了一个行为框架，将一个通用的 LLM“校准”成一个特定领域的专用 Agent。

## 谁写的？

系统指令有两个来源：

1.  **Agent 开发者**：他们编写了大部分基础指令，定义了 Agent 的核心能力和行为模式。这是你无法修改的部分。
2.  **你 (用户)**：大多数 Agent 工具都提供了自定义指令的入口，例如 `CLAUDE.md`、`.aiscript` 或设置中的自定义指令框。

## 关键洞察：用户自定义是最强杠杆

用户自定义的系统指令，是普通用户能用来影响 Agent 行为的**最强大杠杆**，没有之一。

你不需要学习写代码，也不需要理解 Agent 的内部实现。你只需要用自然语言写清楚你的规则和期望，就能在全局范围内改变 Agent 的行为。

想让它遵循团队独特的代码风格？写进系统指令。
想让它避免接触某个敏感模块？写进系统指令。
想让它在每次提交前都执行特定检查？写进系统-指令。

这些用户层面的指令通常会被追加到 Agent 的基础指令之后，或者通过特定语法覆盖默认行为。你花半小时精心打磨的几十行指令，可能比你花几天时间去适配 Agent 本身更有效。

## Prompt 是可维护资产

别把你的系统指令当成一次性的便条。它是一份**活的文档，是需要像代码一样维护的资产**。

- **版本化**：用 Git 管理你的指令文件，追踪每次变更。
- **Review**：让同事 review 你的指令，就像 review 代码一样。
- **迭代**：根据 Agent 的行为反馈，持续优化和追加新规则。

一份好的系统指令集，是你所在项目知识沉淀的一部分。

## 横切关注点

- **上下文流动**：系统指令是上下文的“静态”部分，由 Agent 开发者和用户预先定义，在整个会話生命周期中几乎不变，为所有后续的动态上下文（用户输入、工具返回等）提供了一个稳定的行为基准。
- **风险提示**：相互冲突的指令（例如，Agent 基础指令和用户自定义指令之间的矛盾）会导致 LLM 行为混乱、不可预测。当 Agent 表现怪异时，检查是否存在指令冲突是一个有效的排查方向。
- **可审计性**：系统指令是完全可读的。你可以查看 Agent 的默认指令和你自己的自定义指令，精确了解是什么在驱动它的行为。这是审计和调试 Agent 行为的起点。
