# 系统指令 (System Instructions)

> **上下文视角**：系统指令是注入每个 API 请求的“宪法”——它为 Agent 设定了身份、规则和目标，是 LLM 收到的第一份、也是优先级最高的上下文。

## 它是如何工作的

上一节说了，Agent 负责编排上下文。系统指令就是 Agent 在**每次** API 请求中最先注入的那份上下文。

你打字之前，它就已经在了。

**── 第 1 轮 ──**

```json
// → REQUEST（agent → LLM API）
{
  "system": "你是一个 AI 编程助手。遵循 Google TypeScript 风格指南。只编写或修改代码，不回答与编程无关的问题。",
  "messages": [{ "role": "user", "content": "帮我写一个斐波那契函数" }]
}
```

```json
// ← RESPONSE（LLM API → agent，SSE 流）
{
  "role": "assistant",
  "content": "function fibonacci(n: number): number { ... }"
}
```

**── 第 2 轮 ──**

```json
// → REQUEST（agent → LLM API）
{
  "system": "你是一个 AI 编程助手。遵循 Google TypeScript 风格指南。只编写或修改代码，不回答与编程无关的问题。",
  "messages": [
    { "role": "user", "content": "帮我写一个斐波那契函数" },
    { "role": "assistant", "content": "function fibonacci(n: number)..." },
    { "role": "user", "content": "加上 JSDoc 注释和输入验证" }
  ]
}
```

`messages` 变长了，但 `system` **一字不变**。对话跑 50 轮，它还是一模一样。系统指令不是对话的一部分——是对话的**规则**。

## 它包含什么

- **身份**：`"你是一个资深前端工程师"`
- **能力**：`"你能读写文件、执行终端命令、搜索代码库"`
- **规则**：`"所有代码必须包含 JSDoc 注释"`
- **目标**：`"帮助用户构建功能完整的 Web 应用"`
- **输出格式**：`"代码修改用 diff 格式呈现"`

这些把通用 LLM 变成你的专属工具。

## 谁写的？

系统指令有两个来源：

1.  **Agent 开发者**：他们编写了大部分基础指令，定义了 Agent 的核心能力和行为模式。这是你无法修改的部分。
2.  **你 (用户)**：大多数 Agent 工具都提供了自定义指令的入口，例如 `CLAUDE.md`、`AGENTS.md` 或设置中的自定义指令框。

## 关键洞察：用户自定义是最强杠杆

用户自定义的系统指令，是你能用来影响 Agent 行为的**最强杠杆**。

你不需要改 agent 的内核代码，也不需要理解它的内部实现。用自然语言写清楚你的规则和期望，就能全局改变 Agent 的行为。

想让它遵循团队独特的代码风格？写进系统指令。
想让它避免接触某个敏感模块？写进系统指令。
想让它在每次提交前都执行特定检查？写进系统指令。

这些用户层面的指令通常会被追加到 Agent 的基础指令之后，或者通过特定语法覆盖默认行为。你花半小时精心打磨的几十行指令，可能比你花几天时间去适配 Agent 本身更有效。

## 怎么写好指令

指令不是"管住" Agent，是帮它融入你的团队。两条实操建议：

### 1. 别说"不要想粉红色大象"

别对 Agent 说"不要删文件"。人和 LLM 一样，看到否定句，注意力反而被吸引到被禁止的动作上。

- ❌ "不要在未请求时使用 delete_file 工具。"
- ✅ "只在用户明确要求'删除'时才使用 delete_file。"
- ✅✅ 写成检查："执行 delete_file 前，验证用户请求包含 'delete' 关键词，否则拒绝。"

告诉它路在哪，别把所有坑都围起来。这叫正向不变量。

### 2. 当新人培训，别当 linter 配

`AGENTS.md` 只写代码风格（"用 tabs 不用 spaces"）？那你只把它当了 linter。把它当新入职的同事，不只告诉规则，还要告诉**"我们怎么做事"**。

修 bug 的流程是"复现 → 测试 → 提交"还是"看日志 → 盲猜"？写下来。你要执行者还是会质疑你的高级工程师？明确说："觉得我的要求会破坏架构时，拒绝我，给替代方案。"

指令是对齐预期的协议。

## Prompt 是可维护资产

别把你的系统指令当成一次性的便条。它是一份**活的文档，是需要像代码一样维护的资产**。

有人把项目级指令文件称为"组织伤疤组织"——每一条禁令背后都是一次真实的踩坑。但指令文件不只是伤疤。那些经过反复验证、沉淀下来的成功做法——同样写在里面。**伤疤告诉 Agent 不要做什么，结晶告诉它应该怎么做。** 两者合起来，才是完整的团队智慧。

- **版本化**：用 Git 管理你的指令文件，追踪每次变更。
- **Review**：让同事 review 你的指令，就像 review 代码一样。
- **迭代**：根据 Agent 的行为反馈，持续优化和追加新规则。

一份好的系统指令集，是你所在项目知识沉淀的一部分。

### 团队级 Prompt 治理

一个人维护指令文件，迭代就行。团队维护同一份指令文件，就需要治理。

**版本化是底线。** 指令文件放进 Git，每次变更都有 commit 记录。半年后你想知道"这条规则是谁加的、为什么加的"——git blame 能告诉你。指令文件不在 Git 里等于不可追溯。

**变更需要 Review。** 改一行指令可能改变 Agent 的全局行为。一个人加了"永远使用 tabs"，另一个人的项目全是 spaces——冲突在下一次会话才暴露。指令文件的变更走 PR 流程，就像改代码一样。Review 的重点不是语法，是"这条规则会影响谁"。

**项目变了，指令也要变。** 技术栈迁移了（从 REST 切 GraphQL）、架构重构了（单体拆微服务）、依赖升级了（换了包管理器）——指令文件里的相关规则需要同步更新。这不是"有空再说"，是"下一个 Agent 会话就会基于过时规则做决策"。

### 什么放指令 / 什么留给运行时

| 特征 | 放进 System Instructions | 留给运行时注入 |
|------|------------------------|--------------|
| 每次会话都需要 | ✅ | |
| 只在特定任务需要 | | ✅（用 Skills 或项目文件） |
| 不到 10 行 | ✅ | |
| 超过 100 行 | | ✅（放文件里，让 Agent 按需读取） |
| 变更频率低（月/季） | ✅ | |
| 变更频率高（天/周） | | ✅（频繁改 system prompt 容易出错） |

## 读每一节时，留意这三件事

- **上下文流动**：系统指令是上下文的"静态层"——每轮请求都原样存在，为后续所有动态上下文（用户输入、工具返回）提供稳定的行为基准。
- **风险**：Agent 基础指令和你的自定义指令冲突时，LLM 行为会变得不可预测。Agent 表现怪异？先查指令冲突。
- **可审计性**：系统指令完全可读——打开 Agent 的默认指令和你自己的自定义指令，就能精确知道什么在驱动它的行为。
